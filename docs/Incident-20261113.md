# 2026-11-13 异常重启：证据与未解决问题

采集日期 2026-11-13，所有人类可读时间为 UTC+8。本文是脱敏调查记录，不是修复验收。
源码检查点为 `400502276ee36358bc817409b06dc3ec50ffa1bd`。

## 已确认的直接原因

panic 记录为 `userspace watchdog timeout: no successful checkins from WindowServer
(2 induced crashes) in 120 seconds`。WindowServer 两次被 watchdog 请求崩溃后仍未退出。
同时 logd、opendirectoryd、configd 最近一次成功 checkin 均为 0 秒前。

两份 watchdog stackshot 中，WindowServer 主线程都停在 IOSurface / IOAcceleratorFamily2
内核互斥锁，锁的拥有者均为 `kernel_task` 的 `IOServiceTerminateThread`，线程 ID 111。
同一线程还持有 IntelAccelerator、IGAccelEventMachine 等线程正在等待的锁。

根据报告的 accelerator UUID 与本机二进制 UUID 精确匹配，持锁线程中的返回地址符号化为：

```text
IOServiceTerminateThread
  -> IOAccel command-queue teardown
  -> IGAccelCommandQueue::commandQueueStop() + 0x29
  -> IGAccelEventMachine::finishEvent(IOAccelEvent*, unsigned int) + 0x1e
  -> IGAccelEventMachine::eventTimeout(int) + 0x70
  -> IGScheduler5::checkForProgress(IGHwCsType) + 0xa4
  -> timed thread wait
```

`IOAccel command-queue teardown` 是栈的路径概括，不是对没有本地符号的 IOAF 帧编造函数名。
两份快照间隔约 40 秒；相同锁拥有者仍在相同检查进度路径。它不是单次瞬时争用。
此证据足以解释桌面无法响应与 watchdog 重启，**不能单独解释 GPU 最初为什么失去进度**。

## 内存与温度

两份旧启动 stackshot 的 WindowServer `residentMemoryBytes` 分别为 **11,814,907,904**
和 **11,814,912,000**，spin 的 footprint 均为 **11.00 GB**。
RSS、footprint、malloc 是不同口径，不能混算。
旧 panic 的 compressor / swap 检查为 OK，IPS 的 thermal pressure 为 nominal。
这支持“本次直接重启路径是桌面服务 watchdog”，不构成排除所有温度、内存或硬件问题的证明。

本轮开始时 load average 曾为 118.66，随后回落至 6.90；系统进程与应用启动活动很多。
单次高 load 不能全部归给 GPU，更不能据此关闭同步或系统服务。
2026-11-13 09:08:46 的 SMC CPU die 样本为 68°C，pmset 当时没有记录热警告或 CPU 限速。
没有持续风扇转速与功耗曲线，不声称已经定位或修复高温。

## 与之前候选的关系

- 实际加载的仍是下游 WhateverXe，UUID `674F04E8-5AC6-3296-84D8-7F4FBB44E54D`。
  本仓库的 BCS wait 诊断构建没有部署，POSH 修改只存在于诊断进程。
- 原生并发计数缺陷和未提交 CB 不归还 active 的缺陷已分别复现；不能直接等同于这次
  CCS 故障或更早 BCS semaphore 卡死。
- 较早纯计数生命周期候选最后短测与首个已留存 hardware error 相差约 94 秒。
  不能因为报错客户是 mediaanalysisd，就排除之前工作负载留下影响的可能。
- 最终源码新增的“完整原生析构后删除未提交私有 POSH”路径，仅构建 / CPU 检查通过。
  该版原生检查卡在 Metal 初始化，**尚未安装候选**，其 819 对象 / 512 次增长检查没有运行。
  这只能排除它在这两个阻塞进程中已执行，不能替较早候选证明安全。
- 私有快照中前 16 个恢复记录均可见同一 stamp index 25，resetOK=1、失败计数未增加；
  此后 calls/returns 继续增长。resetOK 是下层返回值，不能当作恢复进度证明。
- 当前预停快照完整采集的是 RCS，寄存器为零且 detail ownership 被拒绝。不能拿它
  当 CCS 故障起点或旧 BCS 等待目标。BCS 与 CCS 是否同源仍未确定。

## 新增用户对照：UU 与 Google Remote Desktop

2026-11-13 整理期间用户补充：“启动 UU 远程的话，必现，但是启动 google remote
desktop 不会出现这个问题”。这是值得优先构造同条件对照的触发差异，尚未由本轮主动复跑。
“必现”没有提供重复次数 / 持续时间，也没有把闪屏、内存增长、卡死和重启分别计数。
此前用户描述为显示远端画面后闪烁；本次“启动”的具体阶段尚未重新确认。

公开材料不能据此断言 Google Remote Desktop 完全不使用 GPU，或认定 UU 的某一个
解码 / 同步 API 就是根因。待核对两客户端的版本、远端目标、分辨率、帧率、编码器、
解码方式、纹理与 IOSurface 复用、提交 / 呈现节奏和持续时间。
优先使用同一远端与显示布局、相同画面和尽量接近的设置，分别采集日志、调用栈、
内存斜率和恢复计数；对照结束后继续观察延迟故障，出现第一项异常即停止。
