  推出“CCS只在RCS reset后才开始异常”。见文末16:24后续复核。

  6，且 POSH LRCA 非零且相同；第二次恢复后 CCS 挂起属于 Windows App context 185。

两次报告都由 `IOAccelEventMachine2` 生成，Application 均为 WindowServer，
hardware context 均为 6，最后 context switch reason 均为
`ELEMENT_SWITCH | WAIT_ON_SCANLINE`，POSH LRCA 均非零且相同（本文不发布地址）。

| 项目 | 09:58:14 | 11:03:42 |

| RCS HEAD/TAIL | 采样位置不同 | 采样位置相同；不独立证明所有执行管线已清空 |
| 未完成单元 | CS、SDE | CS |
| Context 6 状态 | 有 pending 命令 | NO ACTIVE ELEMENTS，arbitration enabled |
| 恢复 | 多次 restart，通道 1/9/30 出现 `no channel associated` | 继续 reset，随后 CCS 故障 |

第二次采样时RCS HEAD/TAIL相同、只有CS未完成；这支持优先检查命令流/上下文状态和等待事件，

证明显示扫描线事件停止；它仍是需要独立验证的线索。

## 16:24 后续复核：标签来源、任务保留与跨引擎时间线

本节更正上文及外部审查的推断，不改变原始事故记录。完整 SHA、CPU 回放边界和
脱敏结论见 [CSB 后续核对](../validation/csb-native-followup-20261116.json)。

### LastContextSwitchReason 的来源

**不成立〔精确部署二进制静态〕：**外部审查 1.3 所说“报告里的 WAIT_ON_SCANLINE
来自 WEX legacyEntry”这条来源归因。accelerator 的 `gatherKeyRingData` 在
`0x2DD5B–0x2DD61` 保存硬件执行列表状态，原生 `dumpExecutionListStatus`
在 `0x45606` 读取该保存值，并在 `0x45864–0x45880` 提取、打印最后切换原因。
部署 WEX 的 `wrapTGLHangRingDump` 在 `0x8F0D9–0x8F0E1` 将原 ring/寄存器参数
交回原生函数，未发现改写这个字段。WEX 的 legacy CSB 转换是另一条路径。

这仍只是**历史切换原因**，不是“采样时正在等扫描线”的证明，也没有独立证明
原生字符串对 Gen12 每一位的语义都正确。两份现场的当前等待位均清，分流结论不变。

### 已接受的 semaphore wait 是否直接丢任务

**不成立〔精确二进制 CPU 回放，限已测串行输入〕：**
“WEX 接受 signal-semaphore wait 后原生直接当完成丢弃”。

实际 WEX consumer `0x127460` 对 detail4 + signal mode 的 ElementWait /
ActiveToIdleWait，调用原生 `ElementSwitch (0x3C5D8)` / `ActiveToIdle (0x3C854)`。
原生经 `moveItemToWaitQueue (0x3C444)` 保存任务、依赖与引用，并跳过容量完成写入；
`evalWaitQueue (0x3B4EE)` 在依赖满足后移回 pending，
`prepareExecListAndSubmit (0x3B9D2)` 在 `0x3BA68` 到达提交入口。

在匿名用户态内存中执行这两个完整 SHA 对应的真实函数，两个分支各测队列索引
1/15/31，共 **6 个正例通过**：依赖未完成时保留，依赖生产者完成后重提交一次，
未将被等待任务自己的 stamp 伪造为完成。另有 **24 个拒绝反例通过**：上述六组
分别测试三个非零 SingleChannelIndex 位组合和不支持的 detail3，均返回 false，
没有完成容量写入或提交。反例只验证 consumer 拒绝，未执行外围 fatal / GPU reset。

外部原子操作按 SDK 契约建模，时钟、遥测/idle、跨引擎通知也建模；最终提交只记录
入口。**未验证真实 IRQ/notify 交付、外层 drain/MMIO、并发及 GPU 完成。**
因此不排除 M2；优先查“依赖生产者未前进／通知或再次调度未发生”，而非给这条
已保留任务的路径新增丢弃、跳等或伪造完成。CPU 回放开发产生的 Python 用户态
SIGSEGV 属于测试夹具错误，不计入自然 GPU / 整机事故。

### channel 29：早于首个记录到的 restart，但引擎归属仍有条件

**成立〔既有整机日志〕：**`11:03:38.981796` 已对 channel 29 发出进度错误，
`11:03:38.981800` 已 signal；首个记录到的 `GPURestartBegin` 在
`11:03:42.000917`，即约 3.019 秒之后。11:03:42 报告中 index29 有
33 个 submitted/returned 差额。这证明其进度错误不是该次 restart 之后才出现。
日志未见同一启动更早的 restart，但不能把日志覆盖当作所有硬件复位均已排除。

**成立〔静态〕：**`eventTimeout` 的默认查表入口 `0x15F67` 指向 `0xA0290`，
index29 对应 engine1/CCS；`notifyAsyncEngines` 在 `0x38869` 使用的另一份
默认表对此一致。**部分成立〔静态＋现场〕：**这支持 CCS 在初始失败批次就已经
涉及其中，但缺故障时完整 flags，尚不能确认。

重要限定：`eventTimeout (0x15F71–0x15F77)` 在 flags 的 `0x18000` 非零时改选
SCI 表。报告的“Multiple channels per index”在 `0x43A79–0x43A93` 只排除
该两位恰为 1，不区分 0/2/3，不能独立证明默认表当时生效。当前启动 flags 为0
也不能代替故障时取值。channel/index29 不是 hardware context185，不能等同。

因此将原先“CCS 只在 RCS reset 后才出问题”收窄为“**CCS 的详细 hang 报告晚于
首个 RCS reset**”。#109 的共享复位机制仍可解释后续恶化，不能据此认定它已解释
首个故障，也不能忽略复位前跨引擎依赖停滞的可能。
