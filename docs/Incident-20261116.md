# 2026-11-16 两次显示卡死：RCS → CCS 恢复链

采集时间 2026-11-16 11:28（UTC+8）。本文是脱敏调查记录，不是修复验收。
本轮没有安装驱动、没有改 EFI、没有主动重启；用户此前已手动重启两次。

## 结论摘要

- **成立〔整机〕：**今天有两次独立卡死，分别开始于 **09:58:11** 和 **11:03:38**。
  两次都先由 WindowServer 的 RCS 上下文报错并进入恢复；第二次在 RCS reset 之后
  又出现 Windows App 的 CCS 上下文反复报错。用户分别在 **10:04**、**11:05**
  手动重启，AppleSMC `Previous shutdown cause: 5`，没有新的 panic 或 watchdog
  spin 文件。
- **成立〔整机〕：**两次 RCS 挂起都发生在同一个 WindowServer hardware context
  6，且 POSH LRCA 非零且相同；第二次恢复后 CCS 挂起属于 Windows App context 185。
- **成立〔整机＋磁盘〕：**当前实际 ESP 上仍是旧 WhateverXe 0.8.0
  (`df96a2ca…d3`，mtime 2026-11-11)。仓库里的 0.8.2
  (`fbd0495d…e79`，mtime 2026-11-16 10:23) **没有写入 ESP**，所以两次卡死和
  当前启动都仍运行 0.8.0；不能说 0.8.2 已经部署或未解决问题。
- **证据不足：**首次故障是 POSH 生命周期、共享 GDRST 破坏兄弟引擎、显示/扫描线
  停摆，还是 0.4.3 Metal 的释放路径，尚未区分。

## 两次 RCS 现场

两次报告都由 `IOAccelEventMachine2` 生成，Application 均为 WindowServer，
hardware context 均为 6，最后 context switch reason 均为
`ELEMENT_SWITCH | WAIT_ON_SCANLINE`，POSH LRCA 均非零且相同（本文不发布地址）。

| 项目 | 09:58:14 | 11:03:42 |
| --- | --- | --- |
| 最后指令记录 | PIPE_CONTROL | 非 PIPE_CONTROL；原始值留本机 |
| RCS HEAD/TAIL | 采样位置不同 | 采样位置相同；不独立证明所有执行管线已清空 |
| 未完成单元 | CS、SDE | CS |
| Context 6 状态 | 有 pending 命令 | NO ACTIVE ELEMENTS，arbitration enabled |
| 恢复 | 多次 restart，通道 1/9/30 出现 `no channel associated` | 继续 reset，随后 CCS 故障 |

第二次采样时RCS HEAD/TAIL相同、只有CS未完成；这支持优先检查命令流/上下文状态和等待事件，
但不能仅凭最后指令记录定位正在阻塞的指令，也不能独立排除此前的着色器或资源错误。
第一次的最后指令记录为PIPE_CONTROL。`WAIT_ON_SCANLINE`只是最后一次context switch的原因，**不能**据此
证明显示扫描线事件停止；它仍是需要独立验证的线索。

## CCS 现场（第二次事件）

- 11:03:52 与 11:04:12 的报告 `Hung/Stuck ring: CCS`，Application 为 Windows App，
  hardware context 185；RCS/其他 ring 处于 NOT enabled 或 idle。
- 三个 CCS 报告的 POSH LRCA 分别为非零的两个不同值和一个全零，说明报告跨越了
  不同恢复阶段；不能把三次 reset 当作同一个未变化的现场。
- 这与既有 #109 / gpurec 分析的“RCS reset 通过共享 GDRST 影响兄弟引擎”方向一致，
  但本机没有部署 gpurec / no-POSH，也没有取得 reset 前后的完整引擎寄存器快照。

## 本轮能成立的因果边界

- 能证明：两次卡死都先表现为 RCS 进度失败；第二次在 RCS reset 后出现 CCS 反复
  失败；恢复循环没有在用户重启前恢复。
- 不能证明：RCS 的初始故障来自 POSH 分配复用、0.4.3 Metal 的私有块释放、
  共享 GDRST、显示引擎停摆或远程客户端 workload；也不能把 `WAIT_ON_SCANLINE`
  直接解释为显示欠载。
- 本轮未取得新的panic / watchdog文件；这不是对所有panic路径均未触发的证明。
  用户明确报告强制重启，不能只凭shutdown cause 5判断为“系统自行重启”。

## 下一步（需另行确认）

1. **不要把仓库里的 0.8.2 当作已经生效的卡死修复。** 实际 ESP 仍是 0.8.0；
   只改数据盘工作副本不会影响启动。是否写入 ESP 要另行决定。
2. **不建议现在就用 0.8.2 替换当前二进制。** 并行整合记录指出：0.8.2 移除了
   `tglProgramRecord`，会同时失去 plane trace；它还是多组件版本变化，不能作为
   RCS/CCS 卡死的单变量 A/B。当前应先完成现有 0.8.0 二进制上的闪屏对照
   （含已暂停的 TGLSyncFlip 候选），再决定是否升级。
3. **卡死的首个单变量方向是 Metal 0.4.3。** 在保持 0.8.0 kext 与 boot-args 不变
   的前提下，按 `Deployment.md` 的步骤回退旧完整 Metal bundle，观察 RCS/CCS
   是否仍复发。回退会恢复已知 POSH 私有块泄漏基线，只用于有界 A/B，不是长期方案。
   如果旧 Metal 仍卡死，再评审 gpurec / no-POSH 共享 reset 候选；不要一次改多项。
4. 每次卡死后保留 `.gpuRestart`、对应时间窗的统一日志和实际加载文件指纹；不要
   覆盖旧报告。下一次卡死后应优先确认是否仍是 context 6 的 RCS 先行、以及是否
   再次出现 CCS 兄弟引擎故障。
5. async flip/显示审计候选不进入这条故障链；它们只处理局部撕裂，且仍未验收。

### 后续决策

暂不安装 generateSync 观测 route，也不部署 gpurec/no-POSH。
优先静态核对**实际下游二进制**的 CSB 翻译、未完成工作保留和重新提交路径，
并核对报告 `LastContextSwitchReason` 的来源，不能拿旧格式标签替代故障时 Gen12 双字。
单独的 generateSync 调用计数不能提供 M2 所缺的链路；inhibit 禁止同步 context switch，
不等于硬件等待本身不可能阻塞，不能仅凭“计数为零／inhibit 存在”排除全部历史故障。

同期整机巡检还发现当前启动内 9 次显示事务失败，其中 6 次在 15:12 熄屏/恢复附近；
后一个窗口返回 `0x2e3`，本机 SDK 定义为 `kIOReturnNoPower`，与断电时序吻合。
它们没有新增 gpuRestart，不能仅凭 error 日志就认定新缺陷或并入本节两次事故。
另见 [整机摘要](../validation/system-audit-20261116.json)。

本轮未改代码、EFI 或显示布局，未部署、重启、运行 GPU 负载或恢复 VA。
